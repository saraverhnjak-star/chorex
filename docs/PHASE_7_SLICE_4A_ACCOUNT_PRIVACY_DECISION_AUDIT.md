## Authority and evidence

Read against AGENTS.md, project documents 00–07 and DECISIONS.md, particularly ADR-016 (Parent-controlled Child custom authentication), ADR-048 (App Check integration without enforcement), ADR-049 (crash reporting only), and OPEN-010/011/014. Also inspected Phase 7 Slice 1 and Slice 3 acceptance, actual Settings composition, Auth providers/client adapter, family/pairing commands, notification workers, schemas and Firestore Rules. The project overview requires immutable operational auditability, but does not define post-deletion retention. Schema section “Contract deadline reminder work” and pending-Reward reminder documentation explicitly say logical records are retained **permanently** for deduplication. That wording conflicts with the proposed full deletion scope if interpreted beyond family existence. This audit does not silently narrow it. Approval must explicitly supersede that retention boundary and update docs 04/06/07 plus the corresponding decision explanation before implementation relies on it. OPEN-010's prohibition on deleting completions to implement undo remains unchanged; full-family administrative deletion requires an explicit separate exception to operational immutability.

Current acceptance remains qualified: controlled iOS non-fatal Crashlytics receipt PASS for both apps; fatal receipt, Android delivery and production symbolication unverified. App Check enforcement OFF; accessibility native traversal and Phase 5 native/push debt remain independent.

## Current lifecycle gaps

Parent Settings is `apps/parent/app/(app)/more.tsx` → `ParentSurface.tsx`; Child Settings is `apps/child/app/more.tsx` → `ChildSurface.tsx`. Both show account information, notification permission/registration, role-specific reminders and sign-out; Parent has family navigation. Neither has Privacy & Data, policy link, export or account deletion.

Both session providers await backend-confirmed current-device registration removal before SDK sign-out. Offline cleanup failure keeps the session for retry. Sign-out removes neither profile, family, Child Auth nor domain history. It does not clear native Firestore disk cache. `createFamily`, `createChild`, `createPairingSession`, `redeemPairingSession` are the current account/family commands; none deletes or transfers ownership. Remaining offer/Contract/review/Reward commands enforce operational transitions, not administrative erasure.

Schema permits multiple Parent memberships and profile familyIds arrays. Client discovery deliberately rejects more than one family. There is no guardian invitation/transfer/voting UI. Deletion must not equate `createdBy` alone with exclusive current authority.

Scope: the authenticated sole Parent may delete their account and its sole family as one administrative operation. Server must verify authoritative membership and discover all affected relationships, not accept a client-selected arbitrary UID/role. A Parent Auth account with no profile/family must have a safe identity-only deletion path after recent-auth and backend orphan/reservation checks; incomplete onboarding must not trap accounts. Fail-safe exceptional cases require a defined support/review path before public release, rather than silently deleting other families or introducing transfer.

### Active obligations and audit retention

**PROPOSED:** administrative hard deletion proceeds irrespective of DRAFT/waiting Offers, ACTIVE, READY_FOR_REVIEW or CHANGES_REQUESTED Contracts, and PENDING_FULFILLMENT or AWAITING_CHILD_CONFIRMATION Rewards. Confirmation must explain loss of family history and unfinished agreements/rewards. It removes records; it does not mark work completed, confirm rewards, write CANCELLED, or settle real-world obligations.

Blocking until all obligations resolve preserves in-app continuity but may trap deletion indefinitely (including a Child who cannot confirm a Reward) and require new cancellation/settlement semantics. Therefore recommend orthogonal administrative erasure, leaving OPEN-011 open. Any later decision to block on cancellation introduces an OPEN-011 dependency and must stop implementation until resolved.

**PROPOSED retention A:** immutable during family/account existence, deletable with approved full-family erasure. Revisions, reviews, completions, activity and reminder deduplication are not permanent archives after deletion. Retention B (audit surviving deletion) needs specified purpose, fields, lawful basis/access and duration; none is currently approved. Do not preserve identifiable terms or actor-linked events “for audit” by default. Deletion-worker metadata is a separate minimal operational exception, proposed below, not retained product history. OPEN-010 remains open; ordinary task undo still cannot delete completions.

## Authentication and failure-safe cleanup proposal

Normal signed-in state is insufficient for an irreversible family operation. Firebase client sensitive operations require recent authentication, but an Admin-driven cascade must enforce its own policy; no client `deleteUser` should run first. **PROPOSED:** explicit password reauthentication through Firebase credential/reauthenticate APIs for current email/password Parents, force refreshed ID token, server verifies authenticated UID, current valid account/provider, active authoritative Parent membership, scope and server-time `auth_time` freshness. Propose a **five-minute maximum** with rejection of absent/malformed/future auth_time. This duration is a ChoreX policy proposal, not Firebase's published automatic threshold. Token refresh alone is not password reauthentication. Do not send passwords to a callable, persist/log them or add security questions. Clear the ephemeral form on completion/cancel. Future providers need their own approved reauth mechanism. [Firebase sensitive-action reauthentication](https://firebase.google.com/docs/auth/ios/manage-users).

**PROPOSED sequence (not implemented):**

1. Validate shared strict Zod input, Auth/recent-auth, server-owned roles and complete relationship inventory. Bind operation to actor, exact scope and idempotency key; reject conflicts. No Admin credentials in app.
2. Durably record authorized operation and bounded progress outside the to-be-deleted family tree. Store only needed UID/entity references, phase/cursor/status, not content/password/tokens. Propose terminal operational retention **seven days**, then purge; unresolved failures remain retryable and alert for intervention, rather than falsely report success. These new records/fields are future design, not actual current collections.
3. Atomically establish account/family deletion fences and disable memberships/access. Every client Rule exception, bootstrap/domain command, pairing redemption/mint, reminder generator, dispatcher and receipt worker must respect fences. Fence `createFamily` as well: otherwise a still-authenticated Parent could recreate private data during cleanup. Current Rules' owner-only device writes do not check membership/profile status and can recreate devices with an existing ID token, so membership removal alone is insufficient.
4. Disable/revoke all affected Child Auth access, invalidate all pairing sessions/retries and pause sending. Keep Parent Auth recoverable until last; fence its product access instead of disabling the only retry route without a worker. Accepted durable work must continue with trusted worker authority even after membership deletion/client disconnect. Client status/retry access, if supplied, must be narrowly bound to the original actor/op and never reopen family access.
5. Drain/fence concurrent commands and external effects, then recursively delete family-owned Offers/revisions, Contracts/tasks/completions/reviews, Rewards, activity/effects, pairing sessions and matching idempotency records. Include partial createChild reservations/Auth identities even without committed membership. Capture event/registration relationships before deleting their parents so indirect push receipts remain findable. Enumerate scoped roots; deleting `families/{id}` alone misses top-level domain data. Deleting a document alone does not delete its subcollections. Recursive cleanup and cross-service Auth changes are not one atomic transaction. [Firestore deletion behavior](https://firebase.google.com/docs/firestore/manage-data/delete-data).
6. Delete all exclusively affected Child user subcollections/profiles and Child Auth identities; tolerate already-missing identities/documents only within the recorded authorized scope. Repeat verification sweeps under the fence. Delete affected receipt/dedup records; repair global cursor only if it points at removed data. Never purge all rate-limit records or a shared job for one family.
7. Delete Parent devices/preferences/profile and family/members when product cleanup is verified. Persist sufficient worker authority/checkpoints for the final phase; do not depend on now-deleted memberships to authorize accepted worker retries.
8. **Delete Parent Auth last.** Persist terminal result using the trusted worker, including recovery when the process crashes immediately after Auth deletion. Report accepted/in-progress distinctly from complete. Keep a minimal deny marker through completion/retry retention where needed to stop stale-token bootstrap/write races; before purging it prove missing-profile checks and token expiry/revocation prevent recreation. No permanent UID archive is implied.

Exact worker trigger/lease/recovery design must be reviewed in Slice 4B. A one-shot callable with an in-memory checklist is unsafe. Reuse existing idempotent Admin architecture but do not treat `createChild`'s two-service reservation as an already implemented deletion framework. The deletion fence must be consulted transactionally by all mutation paths so an in-flight mutation either commits before fence (then is swept) or fails/retries after fence. Custom token minting and Expo sending outside transactions need explicit race handling and rechecks; an already-issued token or already-sent push cannot be recalled by removing a document.

## Child sessions, push and local teardown

Auth deletion/disable invalidates refresh sessions; existing ID tokens are short-lived and can remain usable unless authorization checks reject them. Firebase documents one-hour ID tokens and separate revocation detection. Rules and server fences must deny family access immediately independent of token expiry. Normal individual-device revocation remains OPEN-014. Current pairing same-key REDEEMED replay can mint again without rechecking membership: deletion must fence both initial redemption and replay, and prevent token-mint recreation of a deleted Child. [Firebase session management](https://firebase.google.com/docs/auth/admin/manage-sessions).

Delete every affected `users/{uid}/devices` registration and reminder preference. ChoreX stores Expo tokens, **not raw native APNs/FCM tokens**. Native token-change signals cause Expo reacquisition; do not invent a native-token collection or direct push backend. Fence reminder generation/dispatch before sweeping activity/effects and indirect receipt bindings. Stop new sends to deleted identities; queued/in-flight Expo/APNs/FCM messages may still arrive and must resolve to inaccessible routes without content disclosure. No exactly-once delivery or remote recall promise. Unregistering push does not sign out a device or revoke OS notification permission.

Local proposal: stop subscriptions/registration reconciliation, reset family/profile/entity/form state and pending notification intents, remove displayed notifications/badges where supported, call SDK sign-out and return Child to pairing / Parent to signed-out onboarding. Deletion teardown must not require the old normal sign-out path to delete an already server-removed registration with invalid Auth; use a confirmed-deletion-specific cleanup path. A server-authoritative deletion signal or auth-invalid outcome should trigger teardown; a generic transient permission/network error alone is not proof of deletion.

Keep the installation UUID and education-seen flag: both support a fresh account and contain no family content. Remove any future account-scoped SecureStore data, but do not wipe all installation configuration or manually handle Firebase refresh tokens. Native Auth persistence remains SDK-managed.

Current native Firestore persistence is used for offline reads; no explicit disabling or clear-on-sign-out code was found. Remote deletion cannot erase previously downloaded offline bytes. Propose logical cache clearing at session/deletion boundary with listeners stopped and proper instance shutdown/reinitialization, and verify both RN Firebase 26.4 and native platforms before shipping. Firebase `clearPersistence` requires an unstarted/terminated instance and is **not secure forensic erasure**; cached data may remain recoverable. Cached UI must be gated against revoked/deleted sessions; a disconnected device cannot discover server deletion immediately. If stronger between-session privacy requires disabling disk persistence, that changes established offline behavior and needs separate explicit approval rather than a silent change. [Firebase native cache API and limits](https://firebase.google.com/docs/reference/ios/firebasefirestore/api/reference/Classes/FIRFirestore).

## Legal and store review gates

Security Model section 12 requires dedicated legal/privacy review before commercial launch. Engineering decisions describe deletion mechanics and minimization; store inventory is drafting input; counsel/product must decide distribution jurisdictions, Child rights/Parent authority, consent/age handling, lawful bases, mandatory exceptions, processor agreements, policy wording, external request handling and applicable export/access rights. No COPPA/GDPR-K compliance, age gate or consent mechanism is inferred.

Apple requires discoverable account deletion for account-creating apps, associated data deletion subject to legal retention, and addresses automatically created accounts; confirm how this applies to the separate Child binary and Parent-mediated flow. [Apple guidance](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion).

Google Play's policy guidance includes an in-app path and an external web resource for apps within scope. A functioning externally accessible deletion request route must be selected for launch; a privacy link alone is insufficient unless it actually provides that route. This does not authorize building the deferred marketing site or dashboard. Confirm separate Parent/Child listing scope. Unsupported/multi-guardian cases need a practical reviewed handling route, not an indefinite unexplained block. [Google Play deletion guidance](https://support.google.com/googleplay/android-developer/answer/13327111).
